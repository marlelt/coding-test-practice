# AI開発基盤

## 1. 目的

AI開発基盤は、ChatGPT・CodexなどのAIを個人開発へ活用する際の共通原則を定義する。

目的は、AIに大量のコードを書かせることではない。

以下を同時に実現することを目的とする。

- 開発速度を高める
- 実装品質を維持・向上する
- 人間の技術理解を深める
- AIを利用した開発方法そのものを改善する
- 将来の個人開発でも再利用可能な開発基盤を作る

AIへ単純作業、定型実装、理解済みの処理を積極的に委任する。

一方で、重要な要件、設計、技術選定、データフロー、認証・認可、セキュリティなどは、人間が理解して判断できる状態を維持する。

AIが生成したコードであっても、重要な処理については人間が説明できることを目指す。

AIは人間の代わりにすべてを判断する存在ではなく、人間が判断・理解・レビューに集中するための支援として利用する。

---

## 2. 適用範囲

この文書では、特定の技術スタックに依存しないAI開発の共通原則を定義する。

以下のような内容は、この文書では固定しない。

- プログラミング言語
- フレームワーク
- ORM
- データベース
- 認証ライブラリ
- テストフレームワーク
- アーキテクチャ
- ディレクトリ構成
- クラス構成
- 関数の分割単位
- プロジェクト固有の設計成果物

これらは各プロジェクトの要件、規模、複雑性、技術スタック、開発体制に応じて判断する。

AI開発基盤では、

> 何を採用するか

ではなく、

> どのように判断し、AIと人間がどのように開発を進めるか

を標準化する。

---

## 3. 基本原則

### 3.1 人間が最終的な意思決定を行う

AIは提案、実装、レビュー、調査を支援する。

最終的な意思決定は人間が行う。

特に以下は、人間が最終判断する。

- 要件
- アーキテクチャ
- データベース設計
- 技術選定
- ライブラリ追加
- セキュリティ方針
- プロジェクトルール
- AI開発基盤
- Pull RequestのMerge

AIの提案をそのまま採用するのではなく、必要に応じて以下を確認する。

- なぜその方法なのか
- どのような影響があるか
- 他の方法はあるか
- 現在のプロジェクトに適しているか

---

### 3.2 必要最小限の変更を行う

Issueの目的達成に必要な範囲を超えて変更しない。

特に以下を、明確な理由や人間の承認なく変更しない。

- Issueと無関係なコード
- 命名規則
- アーキテクチャ
- ディレクトリ構成
- 依存ライブラリ
- ライブラリのバージョン
- データベース設計
- プロジェクトルール

改善点を発見した場合は、現在のIssueへ勝手に含めない。

必要に応じて改善案として提示し、人間が現在のIssueで対応するか、別Issueとするか、対応しないかを判断する。

---

### 3.3 既存の決定事項を優先する

一般的なベストプラクティスより、対象プロジェクトですでに決定した内容を優先する。

既存の設計やルールと異なる方法が適切だと考える場合、AIは勝手に変更しない。

以下を説明する。

- 現在の方針
- 現在の方針に存在する問題
- 変更案
- 変更する理由
- 変更による影響
- 必要に応じて代替案

最終的な変更判断は人間が行う。

---

### 3.4 AI生成コードを人間がレビューする

AIが生成したコードであっても、人間による確認を行う。

主に以下を確認する。

- 要件を満たしているか
- Issue外の変更がないか
- 想定した設計になっているか
- データフローが理解できるか
- セキュリティ上の問題がないか
- 必要なテストが存在するか
- 既存ルールへ違反していないか

AIが生成したという理由だけで正しいと判断しない。

---

### 3.5 重要なコードは人間が説明できる状態にする

AI生成コードのすべてを1行ずつ説明できる必要はない。

一方、重要な機能については、少なくとも以下を説明できる状態を目指す。

- なぜこの設計にしたか
- データがどのように流れるか
- 主要なコンポーネントの役割
- 重要なコードが存在する理由
- 他にどのような方法があるか
- なぜ今回の方法を選択したか
- セキュリティ上重要な点

重要な機能では、人間が説明できることも完了条件の一部として扱う。

---

### 3.6 過剰設計を避ける

学習目的や将来必要になるかもしれないという理由だけで、不要な設計を追加しない。

特に以下を目的なく追加しない。

- 抽象化
- レイヤー
- クラス
- デザインパターン
- ライブラリ
- アーキテクチャ
- 設計成果物

現在の要件、規模、複雑性に対して必要な設計を行う。

設計上の問題が実際に発生した場合に、その問題を解決する設計手法やパターンを学び、採用する価値があるか判断する。

目的は高度な設計を採用することではない。

以下を満たす設計を目指す。

- 要件を満たす
- 理解できる
- 変更できる
- 必要以上に複雑ではない

---

## 4. 人間・ChatGPT・Codexの役割

### 4.1 人間

人間は最終意思決定者として、主に以下を担当する。

- 要件の決定
- 重要な設計判断
- 技術選定
- AIへの実装依頼
- diff確認
- AI生成コードの理解
- テスト結果の確認
- レビュー結果の確認
- Pull Requestの確認
- Merge判断
- プロジェクトルール変更
- AI開発基盤変更

AIを利用して作業量を減らしても、重要な判断までAIへ委任しない。

---

### 4.2 ChatGPT

ChatGPTは主に以下を支援する。

- 要件整理
- 設計相談
- 技術選定の比較
- 実装前の学習
- Codexへの実装指示の整理
- Codexが実装したコードの解説
- コードレビュー支援
- Git / GitHub運用支援
- Issue作成支援
- Pull Request作成支援
- Issue完了時の引き継ぎ作成
- AI開発基盤の改善支援

ChatGPTは最終意思決定者ではない。

ChatGPTが実際のコード、文書、リポジトリなどを参照できる場合は、必要に応じて実際の情報を確認して支援する。

実際に確認していない情報について、確認したものとして扱わない。

---

### 4.3 Codex

Codexは主に以下を担当する。

- リポジトリ内のコード確認
- 既存コードに合わせた実装
- 定型実装
- 機械的変更
- テスト実装
- lint・テスト・buildなどの実行
- コードレビュー
- リポジトリ全体を踏まえた問題検出

Codexは実装の主担当として積極的に利用する。

ただし、重要な要件や設計をCodexだけで決定しない。

---

## 5. 判断権限

基本的な判断権限は以下とする。

| 判断 | 人間 | ChatGPT | Codex |
| --- | --- | --- | --- |
| 要件 | 決定 | 提案 | 情報提供 |
| アーキテクチャ | 決定 | 提案 | 提案 |
| データベース設計 | 決定 | 提案 | 提案 |
| ライブラリ追加 | 承認 | 提案 | 提案 |
| 実装詳細 | 最終確認 | 提案 | 主担当 |
| リファクタリング | 承認 | 提案 | 提案 |
| テスト実装 | 確認 | 提案 | 主担当 |
| コードレビュー | 最終判断 | 支援 | 実施 |
| プロジェクトルール変更 | 決定 | 提案 | 提案 |
| AI開発基盤変更 | 決定 | 提案 | 提案 |
| Pull Request Merge | 決定 | 支援 | 実施しない |

AIが判断を支援しても、最終的な責任と意思決定は人間が持つ。

---

## 6. 学習方針

AIによる開発速度だけでなく、人間の技術力向上を重視する。

ただし、すべてを実装前に完全理解してから進める必要はない。

学習対象を以下の3段階に分ける。

### 6.1 必ず理解する

以下は重要度が高いため、人間が理解する。

- アーキテクチャ
- データベース設計
- 認証・認可
- データフロー
- Server / Clientの境界
- セキュリティ
- 状態管理
- 重要な型
- エラーハンドリング方針

---

### 6.2 レビュー時に理解する

以下は実装前に完全理解していなくてもよい。

AIの実装後にコードを教材として理解する。

- ライブラリAPI
- フレームワークの一般的なパターン
- Utility処理
- 関数分割
- 一般的な言語構文
- 定型的な実装パターン

---

### 6.3 AIへ委任してよい

以下は積極的にAIへ委任する。

- import
- 単純な型注釈
- ボイラープレート
- 機械的な変更
- フォーマット
- すでに理解しているパターンの反復

人間の学習効果が低い作業へ時間を使いすぎない。

---

## 7. 学習タイミング

重要な機能では、以下の流れを基本とする。

```text
実装前
↓
何を作るか理解
↓
なぜ必要か理解
↓
重要な仕組みを理解
↓
重要な設計判断を確認
↓
Codex実装
↓
人間がdiff確認
↓
ChatGPTで実装内容を理解
↓
必要なテスト・レビュー
↓
人間が最終判断
```

実装前にすべてのコードを理解する必要はない。

実装後のコードを教材として利用することも学習工程に含める。

重要なのは、

> AIに任せた結果、人間が何も理解していない状態を作らないこと

である。

---

## 8. 設計成果物の方針

### 8.1 必要な成果物だけを作成する

設計成果物を作成すること自体を目的にしない。

プロジェクトの規模、複雑性、変更頻度、開発人数などを踏まえて必要な成果物を判断する。

例えば以下の成果物は、必要になった場合に作成する。

- 要件定義
- 基本設計
- GitHub Issue
- ER図
- API仕様
- 画面設計
- 機能仕様
- シーケンス図
- ADRなどの設計判断記録

すべてのプロジェクトですべての成果物を作成する必要はない。

---

### 8.2 情報の二重管理を避ける

コード、スキーマ、設定ファイルなどから明確に分かる情報を、別の文書へ機械的に複製しない。

同じ情報を複数箇所で管理すると、変更時に不整合が発生する可能性がある。

可能な限り、一つの基準情報へ集約する。

文書には、コードだけでは分かりにくい以下の情報を優先して残す。

- なぜその設計にしたか
- どのような制約があるか
- どのような選択肢を比較したか
- なぜその方法を選択したか
- 将来変更する場合の注意点

---

### 8.3 文書の責務を意識する

一つの文書へ異なる目的の情報を過剰に詰め込まない。

例えば画面仕様、機能仕様、API仕様、データベース仕様などは、複雑性が高くなった場合には責務を分けることを検討する。

一方、小規模なプロジェクトで十分に理解・管理できる場合は、文書を細かく分割しすぎない。

文書構成も過剰設計しない。

---

## 9. AI成果物の出力方針

### 9.1 Markdown成果物

GitHub Issue、Pull Request本文、README、設計書、ルール、チェックリスト、テンプレート、引き継ぎなど、Markdownファイルへ貼り付けることを目的とする成果物は、レンダリング済みMarkdownではなくコピー可能なMarkdown原文として出力する。

Markdown原文はコードフェンス内へ出力する。

成果物内部にトリプルバッククォートが存在する場合は、外側に4つ以上のバッククォートを使用する。

人間が明示的に別形式を指定した場合は、その指示を優先する。

---

### 9.2 文書修正時は完成版全体を出力する

既存のMarkdown文書を修正・追記する場合は、原則として変更箇所だけではなく、修正後の文書全体を出力する。

これは、人間が以下を確認しやすくするためである。

- 修正内容が文書全体と矛盾していないか
- 既存の重要な内容が失われていないか
- 見出し構成や番号が崩れていないか
- 修正後の内容をそのまま既存ファイルへ置き換えられるか

人間が明示的に差分のみを求めた場合は、変更箇所のみを出力してよい。

Markdownファイルとして使用する成果物は、修正後の完成版全体をコピー可能なMarkdown原文として出力する。

---

### 9.3 言語

説明、設計、Issue、Pull Request、ドキュメント、コメントなどは日本語を基本とする。

以下は必要に応じて英語を使用する。

- 固有名詞
- 技術名称
- API
- ライブラリ名
- ファイル名
- コード
- コマンド
- 規格名
- 一般的に英語表記する技術用語

不要な英語の概念名や見出しを増やさない。

---

## 10. 外部サービスとの連携

AIとGitHub、クラウド、データベース、MCP、外部SaaSなどの外部サービスを連携することを、AI開発の必須条件としない。

外部サービスとの連携は、利便性だけを理由に導入しない。

導入前に、必要に応じて以下を確認する。

- 連携する目的
- 連携によって得られる効果
- AIがアクセス可能になるデータ
- 必要な権限
- 読み取り権限だけで目的を達成できないか
- 書き込み権限が本当に必要か
- 秘密情報や個人情報へのアクセス
- 本番環境への影響
- データの保存・利用方法
- 人間がAIの操作や成果を確認できるか
- 問題発生時に連携を停止できるか

可能な場合は、以下の順序で段階的に導入する。

```text
外部サービスと連携しない
↓
対象を限定して読み取り権限のみを与える
↓
必要性を確認する
↓
必要な追加権限のみを許可する
```

書き込み権限、本番環境へのアクセス、秘密情報へのアクセスなど、影響の大きい権限は利便性のみを理由に付与しない。

外部サービスとの連携を導入する最終判断は人間が行う。

## 11. Issue完了時の引き継ぎ

Issue完了時には、次のIssue用ChatGPTチャットへ渡す引き継ぎを作成する。

最低限、以下を含める。

- 現在のプロジェクト状態
- 完了したIssue
- 主な変更内容
- 設計・技術上の決定事項
- 関連する技術スタック・設定
- Git / GitHubの状態
- 次のIssue
- 注意事項
- 継続するプロジェクトルール
- AI開発基盤上の重要なルール

会話全文をコピーするのではなく、次のIssueに必要な情報へ圧縮する。

詳細なルールや文書の全文を引き継ぎへ複製する必要はない。

次のIssueで参照可能な基準文書が存在する場合は、その文書を基準とし、引き継ぎには現在状態や直近の重要な決定を中心に残す。

引き継ぎはMarkdown原文として出力する。

---

## 12. AI開発基盤の改善

AI開発基盤を固定された完成形とは考えない。

実際の開発で問題が発生した場合、必要に応じて原因を分析する。

例えば以下のような問題を改善対象とする。

- AIがIssue外の変更を行った
- 既存ルールを無視した
- 不要なライブラリを追加した
- Codexへの依頼が曖昧だった
- レビューで問題を見落とした
- 人間が実装を理解できなくなった
- ChatGPTの説明方法が適切でなかった
- Markdown成果物の形式が崩れた
- 文書修正時に変更箇所だけが提示され、完成状態を確認しづらかった
- Issue間の引き継ぎが不足した
- 不要な設計成果物を作成した
- 同じ情報を複数箇所で管理することになった

問題が発生した場合は、以下を確認する。

1. なぜ問題が発生したか
2. 一時的な問題か、繰り返す可能性があるか
3. どのルールや工程で防止できるか
4. ルール追加による負担が大きすぎないか

改善先の例:

```text
複数プロジェクト共通の問題
→ foundation.md / workflow.md

プロジェクト固有の問題
→ project-rules.md

Codexへの依頼方法
→ prompts.md

レビュー漏れ
→ review-checklist.md

ChatGPTの振る舞い
→ ChatGPTのプロジェクト設定

一時的なIssue固有情報
→ Issue / 引き継ぎ
```

一度発生した問題をすべてルール化しない。

繰り返し発生する問題や、発生時の影響が大きい問題を優先して改善する。

---

## 13. v1の方針

AI開発基盤v1では、

> 人間 + ChatGPT + Codex

によるシンプルなAI開発を基本とする。

v1の段階では、以下を目的にしない。

- AIによるIssueの完全自動作成
- AIによるPull Requestの完全自動作成
- GitHub Actionsによる大規模なAIレビュー自動化
- 多数のMCP連携
- マルチエージェント構成
- RAGによるルール管理
- 独自AIツールの大量開発
- 複雑なプロンプト管理基盤
- ADRなどの設計成果物の自動大量生成
- AI開発基盤そのものの大規模なシステム化

まずはシンプルな運用で実際の開発を行う。

問題が発生した場合に、その問題を解決するための仕組みを追加する。

AI開発基盤そのものを過剰設計しない。

---

## 14. 中心原則

AI開発基盤の中心となる考え方は以下である。

> AIに実装を任せ、人間は判断・理解・レビューに集中することで、開発速度・品質・学習速度を同時に高める。

AIを利用する目的は、人間の判断をなくすことではない。

人間が重要な判断へ集中できる状態を作ることである。

AIへ任せる範囲を広げながらも、

- 要件を理解する
- 設計を理解する
- 重要なコードを理解する
- レビューする
- 最終判断する

という人間の役割を維持する。

この原則を基準として、AI開発基盤を継続的に改善する。
