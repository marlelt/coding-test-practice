# プロジェクトルール

## 1. 目的

この文書では、コーディング試験対策アプリ固有の開発ルール、技術方針、設計上の決定事項を定義する。

AI開発全体の共通原則については、`docs/ai-development/foundation.md` を参照する。

この文書は、このプロジェクト固有のルールを管理するための基準文書として扱う。

ChatGPT・Codexは、一般的なベストプラクティスより、この文書および対象Issueで決定した内容を優先する。

既存ルールと異なる方法が適切だと考える場合、AIは勝手に変更せず、以下を説明する。

- 現在の方針
- 現在の方針に存在する問題
- 変更案
- 変更する理由
- 変更による影響
- 必要に応じて代替案

最終的な変更判断は人間が行う。

---

## 2. プロジェクト概要

このプロジェクトでは、コーディング試験の学習・練習を行うWebアプリケーションを開発する。

### 2.1 開発背景

実際のコーディング試験を受験した際、通常のWebアプリケーション開発とは異なる以下の能力が必要であることを実感した。

- アルゴリズム
- データ構造
- 標準入力
- 標準出力
- 制限時間内での問題理解
- 制限時間内での実装
- 計算量を意識した問題解決

実務でWebアプリケーションを開発できることと、コーディング試験を解けることは同じではない。

そのため、自分自身が体系的にコーディング試験を学習・練習できる環境を作る。

---

### 2.2 アプリケーションとしての目的

主な目的は以下。

- アルゴリズムを学習する
- データ構造を学習する
- 問題解決能力を高める
- 標準入力・標準出力に慣れる
- コーディング試験形式に慣れる
- コードを実行する
- テストケースによって結果を確認する
- 実際の試験を想定した練習を行う

開発者自身を最初のユーザーとして利用する。

アプリケーション開発中にアルゴリズム、データ構造、標準入力・標準出力などが実装と関係する場合は、その都度必要な範囲で学習する。

問題演習が可能な状態になった後は、このアプリケーションを利用して体系的にコーディング試験対策を行う。

実際に利用して発見した不便や不足機能は、必要に応じてアプリケーション改善へ反映する。

---

### 2.3 使用言語と学習目的の分離

アプリケーション開発では、TypeScript / Next.jsを使用する。

これは、バックエンド中心の経験からフロントエンドを含むフルスタック開発能力を広げることも目的としている。

一方、コーディング試験の問題演習では、当面PHPを主に使用する。

コーディング試験では、慣れているPHPを利用することで、言語仕様ではなく以下へ集中する。

- 問題理解
- アルゴリズム
- データ構造
- 計算量
- 標準入力・標準出力
- 制限時間内での実装

アルゴリズムやデータ構造そのものは言語非依存として理解する。

必要に応じてPHPとTypeScriptを比較する。

PHPを使用する方針は現時点の学習方針であり、将来の要件や学習目的によって変更する可能性はある。

---

### 2.4 開発プロジェクトとしての目的

このアプリケーションを完成させることだけを目的にしない。

開発を通して以下を学習する。

- Next.js
- React
- TypeScript
- フルスタックWeb開発
- データベース設計
- 認証・認可
- テスト
- CI
- セキュリティ
- AIを利用した開発
- 設計と責務分割
- 必要に応じたDDDの考え方

AIへ実装を委任しながらも、重要な設計やコードを人間が説明できる状態を目指す。

## 4. アプリケーション構成

Next.js App Routerを使用する。

現時点では、Next.jsによるフルスタック構成とする。

バックエンドAPIについては、Next.js Route Handlersを使用する。

現時点では、フロントエンドとバックエンドを別アプリケーションとして分離しない。

将来、要件や複雑性によって分離する必要が発生した場合は、その時点で再検討する。

将来必要になる可能性だけを理由に、事前に構成を複雑化しない。

## 5. 設計方針

### 5.1 DDD Lite

このプロジェクトでは、DDDを実装すること自体を目的にしない。

DDD Liteとして扱い、実際の設計課題に対して有効な考え方のみを段階的に採用する。

学習目的だけで以下を事前に大量導入しない。

- Domain層
- Application層
- Infrastructure層
- Presentation層
- Entity
- Value Object
- Repository
- Domain Service
- Application Service
- Factory

実際に、

> このロジックをどこへ置くべきか

という問題が発生した場合に、

1. 現在の設計上の問題を確認する
2. DDDではどのように考えるか学習する
3. このプロジェクトで問題解決に有効か判断する
4. 必要であれば採用する

という順序で進める。

---

### 5.2 過剰設計を避ける

現在の要件、規模、複雑性に必要な設計を行う。

以下を理由なく追加しない。

- 抽象化
- レイヤー
- クラス
- デザインパターン
- ライブラリ
- 設定
- 設計成果物

将来必要になるかもしれないという理由だけで実装しない。

---

### 5.3 既存設計との一貫性

新しい実装では、既存コードや既存設計との一貫性を確認する。

一般的なベストプラクティスと異なることだけを理由に既存設計を変更しない。

既存設計に問題がある場合は、現在のIssueへ勝手に変更を含めず、必要に応じて改善案として扱う。

---

## 6. 設計成果物の方針

設計成果物を作成すること自体を目的にしない。

このプロジェクトでは、基本的に以下を中心として開発する。

- 要件定義
- 基本設計
- GitHub Issue
- ソースコード
- Pull Request

複雑性が高まり、これらだけでは理解や管理が難しくなった場合に追加の設計成果物を検討する。

追加候補の例:

- ER図
- API仕様
- 画面設計
- 機能仕様
- シーケンス図
- ADRなどの設計判断記録

---

### 6.1 データベース定義

このプロジェクトでは、`prisma/schema.prisma` をデータベース構造の主要な基準として扱う。

以下のような構造情報は、原則としてPrisma schemaから確認する。

- モデル
- フィールド
- 型
- NULL許可
- 主キー
- デフォルト値
- リレーション
- PostgreSQL上のテーブル名・カラム名との対応

そのため、現在の規模では従来型のテーブル定義書を別途作成しない。

ただし、以下のような設計意図は必要に応じて基本設計やプロジェクトルールへ残す。

- なぜテーブルを分割したか
- リレーションの意図
- 削除方針
- データ保持方針
- 将来へ影響する重要な制約

Prisma schemaだけでは理解が難しくなった場合は、ER図やデータベース設計文書の追加を検討する。

---

### 6.2 API・画面・機能仕様

API仕様書、画面設計書、機能仕様書を最初から必須成果物としない。

基本設計、Issue、コードから十分に理解できる場合は追加しない。

複雑性が高まり、責務や仕様を分離して管理する必要が発生した場合に作成する。

同じ情報を複数文書へ機械的に複製しない。

---

## 7. Next.js / React方針

Next.js App Routerを使用する。

Server ComponentとClient Componentの責務を意識する。

Client Componentが必要な場合は、その理由を理解したうえで使用する。

ブラウザ側で不要な処理やデータをClientへ渡さない。

Route HandlersをバックエンドAPIとして利用する。

Server / Clientの境界は重要な学習対象として扱う。

Next.jsの一般的なパターンを採用する場合でも、プロジェクトの現在の要件に対して必要か確認する。

---

## 8. TypeScript方針

TypeScriptの型を活用する。

特に以下を意識する。

- 重要なデータ構造へ適切な型を付ける
- 不要な `any` を避ける
- `null` / `undefined` を適切に扱う
- 型アサーションによって問題を隠さない
- 外部入力をTypeScriptの型だけで信用しない
- 型を過剰に複雑化しない

重要な型については、人間がその意味を説明できる状態を目指す。

---

## 9. Prisma / データベース方針

PrismaをORMとして使用する。

Prisma Clientの出力先は以下。

```text
src/generated/prisma
```

Prisma ClientからPostgreSQLへ接続する。

`DATABASE_URL` が存在しない場合は、設定不足を早期に検出する。

開発環境では、不要なPrisma Clientの再生成や接続増加を避けるため、必要に応じて既存の仕組みを利用する。

---

### 9.1 命名

Prisma schemaではTypeScript側の扱いやすさを考慮してcamelCaseを使用する。

PostgreSQLではsnake_caseを使用する。

必要に応じて `@map` / `@@map` を使用して対応させる。

---

### 9.2 主キー

現在の主要テーブルでは、主キーとして整数IDを使用する。

基本形:

```prisma
id Int @id @default(autoincrement())
```

主キー方式を変更する場合は、理由と影響を確認してから判断する。

---

### 9.3 ユーザー削除

ユーザー削除は論理削除を基本とする。

`deleted_at` を使用する。

ユーザーに関連する学習履歴や提出履歴を安易に物理削除しない。

---

### 9.4 問題公開状態

問題の公開状態は `is_published` で管理する。

公開状態の管理方法を変更する場合は、問題管理機能の要件を確認して判断する。

---

### 9.5 削除時のリレーション

現在の基本方針は以下。

- Problem → TestCase: Cascade
- User → Submission: Restrict
- Problem → Submission: Restrict
- Submission → ExecutionResult: Cascade
- TestCase → ExecutionResult: Restrict

削除ルールはデータ保持方針へ影響するため、AIだけで変更しない。

---

## 10. 現在の主要データモデル

現在の主要モデルは以下。

- User

- TestCase
- Submission

概念上の主な関係は以下。

## 11. 環境変数

秘密情報をソースコードへ直接記載しない。

データベース接続情報、認証用秘密情報、外部サービスのAPIキーなどは環境変数で管理する。

`.env` など秘密情報を含むファイルをGitへ誤ってコミットしない。

Client側へ秘密情報を送信しない。

新しい環境変数を追加する場合は、用途と必要性を確認する。

## 12. Git / GitHub運用

基本単位は以下。

> 1 Issue = 1 ChatGPTチャット = 1 Codexセッション = 1 feature branch = 1 Pull Request

基本フロー:

```text
requirements.md
↓
basic-design.md
↓
docs/issue-plan.md
↓
GitHub Issue
↓
GitHub Projectsで管理
↓
Issue単位の開発
```

`docs/issue-plan.md` は、要件定義・基本設計で決定した内容を実装可能なIssueへ分解し、実装順序・全体計画を整理するために使用する。

新しいIssueを追加する場合や、既存Issueの目的・範囲を大きく変更する場合は、必要に応じて `docs/issue-plan.md` との整合性を確認する。

ただし、GitHub Issueと `docs/issue-plan.md` の内容を機械的に二重管理することは目的としない。

Issue単位の基本フロー:

```text
Issue
↓
feature branch
↓
設計・必要な学習
↓
Codex実装
↓
diff確認
↓
テスト
↓
レビュー
↓
Pull Request
↓
Files changed確認
↓
Squash and Merge
↓
feature branch削除
↓
main更新
↓
次Issueへの引き継ぎ
```

---

### 12.1 GitHub Label

このプロジェクトでは、以下のLabel体系を使用する。

#### area

- `area:backend`：Next.js / API / DB設計 / ドメインロジック
- `area:ci`：GitHub Actions / Lint / Test自動化
- `area:frontend`：Next.js / UI / 型定義 / APIクライアント
- `area:infra`：Docker / 環境構築 / PostgreSQL

#### size

- `size:S`：0.5人日
- `size:M`：1人日
- `size:L`：2人日
- `size:XL`：4人日以上

#### type

- `type:bug`：バグ修正
- `type:docs`：ドキュメント
- `type:feature`：新機能
- `type:infra`：Docker / 環境
- `type:refactor`：既存コードの改善（機能追加なし・振る舞いは変えない）
- `type:test`：テスト

Issue作成時およびIssue開始時には、Issue内容に対応するLabelが適切に設定されていることを確認する。

該当する `area:*` がない場合は、無理にarea Labelを付ける必要はない。

---

### 12.2 feature branch

Issueごとにfeature branchを作成する。

Issueと無関係な変更を同じfeature branchへ混在させない。

---

### 12.3 コミットメッセージ

Conventional Commitsを基本とする。

説明部分は日本語を使用する。

例:

```text
feat: 認証機能を追加
```

```text
fix: Prisma接続設定を修正
```

```text
docs: AI開発ルールを追加
```

---

### 12.4 Pull Request

Issueの作業と確認が完了してからPull Requestを作成する。

Pull Requestでは最低限以下を確認する。

- Issueの目的を満たしている
- 完了条件を満たしている
- Issue外の変更がない
- 必要なテストが完了している
- 重大なレビュー指摘が残っていない
- 重要な実装内容を人間が理解している

Merge前にはFiles changedを人間が確認する。

---

### 12.5 Merge

基本的にSquash and Mergeを使用する。

Mergeの最終判断は人間が行う。

AIは自動的にMergeを決定しない。

---

### 12.6 Merge後

Merge後は以下を行う。

1. Pull Requestが正常にMergeされたことを確認する
2. Issueが完了していることを確認する
3. remoteのfeature branchを削除する
4. localのfeature branchを削除する
5. mainへ切り替える
6. remoteのmainを取得する
7. ローカルmainを最新状態にする
8. 次Issueへ進める状態になっていることを確認する
9. 次Issue用ChatGPTチャットへの引き継ぎを作成する

---

## 13. ChatGPTからのGitHub参照

現在、このプロジェクトではChatGPTから対象のGitHubリポジトリを参照できる連携を利用している。

この連携は、ChatGPTが必要に応じて以下を実際に確認するために利用する。

- リポジトリ内のAI開発基盤
- プロジェクトルール
- 設計文書
- Issue
- Pull Request
- ソースコード
- 設定ファイル
- その他、判断に必要なリポジトリ情報

GitHub連携が存在することを理由に、ChatGPTがリポジトリ全体を常に確認済みであるとは扱わない。

ChatGPTは、実際に取得・確認していないファイルやコードについて「確認した」「読んだ」と表現しない。

重要な設計判断、Codexへの実装指示、コードレビュー、ルール確認などでリポジトリ内の最新情報が必要な場合は、必要に応じてGitHub連携を利用して実際の情報を取得する。

GitHubへまだpushされていないローカル変更は、GitHub連携から参照できない。

未pushの変更が重要な判断に必要な場合は、現在のチャットで共有された以下の情報を利用する。

- コード
- diff
- Markdown文書
- Codexの出力
- その他のローカル変更内容

現在のチャットで共有された未pushの内容とGitHub上の内容が異なる場合は、共有された最新のローカル内容を優先する。

このGitHub連携は、このプロジェクトで実際に許可された対象リポジトリの範囲で利用する。

他のリポジトリや外部サービスへのアクセスを前提としない。

## 14. AI利用時のプロジェクト固有ルール

### 14.1 Laravel / PHPとの比較

ユーザーはLaravel / PHPの実務経験があり、Next.js / TypeScriptは学習対象である。

Next.js、React、TypeScript、Prisma、Auth.jsなどを説明するときは、理解に有効な場合Laravel / PHPと比較する。

基本的には以下の順序で説明する。

1. Next.js / TypeScript側の仕組み
2. Laravel / PHPで近い概念
3. 共通点
4. 相違点

異なる概念を完全に同じものとして説明しない。

---

### 14.2 AI生成コードを理解する

AIへ実装を委任しても、重要なコードを理解しないままMergeしない。

特に以下は人間が理解する。

- アーキテクチャ
- データベース設計
- 認証・認可
- データフロー
- Server / Clientの境界
- セキュリティ
- 状態管理
- 重要なTypeScriptの型
- エラーハンドリング方針

ライブラリAPIや一般的な構文などは、必要に応じて実装後に学習する。

---

### 14.3 重要な設計をCodexへ丸投げしない

重要な機能では、実装前に人間とChatGPTで必要な設計を確認する。

特に以下は事前確認を重視する。

- 認証
- 認可
- データベース設計
- セキュリティ
- 外部API
- コード実行
- アーキテクチャへ大きく影響する変更

設計確認後にCodexへ実装を依頼する。

---

### 14.4 不要な変更を行わない

AIはIssueの目的達成に必要な範囲を超えて変更しない。

以下を勝手に行わない。

- Issue外のリファクタリング
- 命名変更
- ディレクトリ再編
- ライブラリ追加
- ライブラリ更新
- アーキテクチャ変更
- データベース設計変更
- プロジェクトルール変更

改善点を発見した場合は提案として扱う。

---

### 14.5 Markdown成果物

GitHub Issue、Pull Request本文、README、設計書、ルール、チェックリスト、テンプレート、引き継ぎなど、Markdownファイルへ貼り付ける成果物はコピー可能なMarkdown原文として出力する。

既存のMarkdown文書を修正・追記する場合は、原則として変更箇所だけではなく、修正後の完成版全体をMarkdown原文として出力する。

ユーザーが明示的に差分のみを求めた場合は、その指示を優先する。

---

### 14.6 日本語を基本とする

説明、設計、Issue、Pull Request、ドキュメント、コメントなどは日本語を基本とする。

技術名称、コード、API、ライブラリ名、コマンドなど、英語表記が自然なものは英語を使用する。

不要な英語の概念名や見出しを増やさない。

---

### 14.7 Issue完了時に引き継ぎを作成する

Issue完了後は、次のIssue用ChatGPTチャットへ渡す引き継ぎを作成する。

引き継ぎには現在状態と直近の重要な決定を中心に記載する。

リポジトリ内の基準文書に存在する詳細なルール全文を、引き継ぎへ機械的に複製しない。

---

## 15. 学習時のプロジェクト固有ルール

### 15.1 アプリケーション開発

TypeScript / Next.jsを使用してフルスタック開発を学習する。

AIへ実装を委任しながら、重要な設計や処理を理解する。

---

### 15.2 コーディング試験

当面PHPを使用する。

言語仕様より以下へ集中する。

- 問題理解
- アルゴリズム
- データ構造
- 計算量
- 標準入力
- 標準出力
- 制限時間内での実装

---

### 15.3 アルゴリズム・データ構造

アプリケーション開発中に関連する概念が登場した場合は、その都度必要な範囲で学習する。

問題演習機能が利用可能になった後は、アプリケーションを利用して体系的に学習する。

実際に利用して発見した問題を、必要に応じてアプリケーション改善へ反映する。

---

### 15.4 DDD

DDDを体系的にすべて実装することを目的にしない。

実際の設計問題が発生した場合に、その問題へ有効なDDDの考え方を学習する。

現在の要件に不要なパターンを学習目的だけで追加しない。

---

## 16. AI開発基盤

このプロジェクトでは、以下のファイルをAI開発基盤として使用する。

```text
AGENTS.md

docs/
└── ai-development/
    ├── foundation.md
    ├── project-rules.md
    ├── workflow.md
    ├── prompts.md
    └── review-checklist.md

.github/
└── pull_request_template.md
```

各ファイルの主な役割は以下。

### `AGENTS.md`

Codexがリポジトリで作業を開始するときの入口として使用する。

詳細なルールをすべて複製せず、必要な基準文書へ案内する。

### `foundation.md`

複数プロジェクトで再利用可能なAI開発の共通原則を定義する。

### `project-rules.md`

このプロジェクト固有の技術方針、設計方針、開発ルールを定義する。

### `workflow.md`

Issue開始からMerge、次Issueへの引き継ぎまでの標準開発フローを定義する。

### `prompts.md`

Codexへの実装、調査、レビュー、修正依頼の基本形式を定義する。

### `review-checklist.md`

AI生成コードをレビューする際の詳細な確認観点を定義する。

人間が毎回すべての項目へチェックを付けるための作業表ではない。

### `pull_request_template.md`

Pull Request作成時の基本構成と、人間がMerge前に行う簡潔な最終確認を定義する。

## 17. 判断の優先順位

このプロジェクトでは、以下の順序を基本的な判断優先順位とする。

1. 対象Issueで明示的に決定した内容
2. `project-rules.md`
3. `foundation.md` / `workflow.md`
4. `AGENTS.md`
5. 一般的なベストプラクティス

`prompts.md` はCodexへの依頼方法の基準として使用する。

`review-checklist.md` はレビュー観点の基準として使用する。

上位の決定と下位のルールが矛盾する場合は、上位を優先する。

ただし、矛盾が意図した変更なのか不明な場合は、AIが独自判断で既存ルールを変更せず、人間へ確認する。

---

## 18. 未確定事項の扱い

重要な内容が未確定の場合、AIが推測して確定しない。

基本的には以下の流れで判断する。

```text
未確定事項を発見
↓
必要性を確認
↓
選択肢を整理
↓
メリット・デメリットを整理
↓
必要に応じてChatGPT・Codexが提案
↓
人間が判断
↓
実装
↓
継続的なルールであれば基準文書へ反映
```

軽微な実装詳細まで毎回人間へ確認する必要はない。

要件、設計、セキュリティ、データ保持、外部サービス、技術選定など、重要な判断へ影響する内容を優先して確認する。

---

## 19. ルール変更

プロジェクトルールを固定された完成形とは考えない。

実際の開発で問題が発生した場合は、必要に応じて改善する。

変更時は以下を確認する。

- なぜ変更するのか
- 現在のルールにどのような問題があるか
- 変更によって何が改善されるか
- 他のルールへ影響しないか
- AI開発基盤の共通ルールへ反映するべき内容か
- ChatGPTの会話開始時からの振る舞いにも影響するか

AIが独自判断でルールを変更しない。

最終的な変更判断は人間が行う。

ChatGPTの安定した振る舞いにも影響する変更の場合は、ChatGPTプロジェクト設定の更新が必要か確認する。

詳細なプロジェクトルールの変更だけを理由に、ChatGPTプロジェクト設定へ同じ内容を全文複製しない。
